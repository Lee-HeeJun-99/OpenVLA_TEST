(여기에 패키지 경로 붙여/lhj)

이번 작업의 목적은 새로 수집한 sim/real 이미지와 로그를 이용하여 기존 sim-to-real 분석을 확장하고, 이후 Shadow Mode 및 실제 rollout 평가로 연결할 수 있는 분석 파이프라인을 완성하는 것이다.

중요한 전제는 다음과 같다.

- 출력 주기와 그리퍼 홈 위치 등 기본적인 초기 조건은 이미 맞춰져 있다.
- OFT는 1 Hz로 입력을 받고, action chunk의 K=5를 5 Hz로 실행한다.
- 현재까지 수행된 실험은 주로 sim/real 이미지, feature, action gap을 비교한 오프라인 분석이다.
- 실제 Shadow Mode 및 closed-loop rollout 결과가 없는 경우, 이를 수행한 것처럼 작성하면 안 된다.
- 기존 `phase1~phase7`의 코드, 데이터 구조, metric, figure 생성 코드, 보고서를 최대한 재사용한다.
- 새 스크립트를 만들기 전에 기존에 같은 기능을 수행하는 코드가 있는지 반드시 확인한다.
- 기존 결과와 파일을 덮어쓰거나 삭제하지 말고, 새로운 출력 디렉터리를 사용한다.
- 경로나 데이터 형식을 임의로 가정하지 말고 실제 저장소와 수집 데이터 구조를 먼저 확인한다.

- false close

- early close

- 모델별

# 11. 통합 분포 분석

이번 연구의 핵심이 분포 분석이라는 점을 반영하여 다음 분포를 구분해줘.

- sim input distribution
- real input distribution

- real representation distribution

1. sim input vs real input
2. sim feature vs real feature
3. 동일 모델의 sim action vs real action
4. OpenVLA vs planner
5. OFT vs planner
6. OpenVLA vs OFT

8. observation gap vs action gap

OOD 비율을 단순 min/max 범위로만 정의하지 말고, 가능하면 다음 방법을 함께 비교해줘.

- bootstrap confidence interval
- permutation test
- paired statistical test
- effect size
- multiple-comparison correction

# 13. Correction 진단

기존 correction, oracle, low-rank direction, phase gate, lambda gate 코드를 최대한 재사용해줘.

단, correction은 다음 조건을 지켜야 한다.

- oracle correction은 실제 적용 가능한 방법이 아니라 성능 상한선 분석으로 표시
- correction direction을 test 데이터에서 선택하지 말 것
- train/validation/test 또는 leave-one-episode-out 구조 유지
- correction 전후 representation collapse 검사
- action gap 감소와 planner GT error 감소를 구분
- sim-real action 일치도가 높아졌더라도 두 action이 동시에 planner에서 멀어질 수 있음을 확인
- 실제 rollout 성능 향상을 증명하지 않았다면 그렇게 주장하지 말 것

low-rank direction은 1, 2, 4, 8, 16, 32, 64, 128개 방향을 사용하고 이것이 원 hidden dimension 자체를 바꾸는 것이 아니라 correction에 사용하는 부분공간의 rank라는 점을 문서에 명시해줘.

다음 조건별로 correction 필요성을 판단해줘.

1. observation gap은 크지만 action gap은 작음
2. observation/representation/action gap이 모두 큼
3. representation gap은 작지만 planner action error가 큼
4. grasp phase와 gripper에서만 gap이 큼
5. camera alignment error와 action gap의 상관이 큼
6. correction 후 sim-real gap은 감소하지만 planner error는 증가함

# 14. Rollout 프로토콜 정리

실제 rollout은 분석 코드 실행과 분리해줘.

## Prototype

시작 위치:

- cube 근처
- cube와 home pose의 중간
- home pose 근처

각 위치에서:

- OpenVLA 5회
- OFT 5회

총 30회다.

## Final closed-loop rollout

- OpenVLA 30회
- OFT 30회
- 총 60회
- 같은 layout에서 두 모델을 paired comparison
- 홀수 layout: OpenVLA → OFT
- 짝수 layout: OFT → OpenVLA
- 각 실행 전 cube와 robot state reset
- instruction은 학습 시 사용한 `pick up the {color} cube`
- cube 위치는 시뮬레이터에 정의된 범위 안에서 배치

기록 항목:

- 성공 여부
- reach failure
- alignment failure
- grasp failure
- lift failure
- timeout
- communication failure
- emergency stop
- completion time
- inference latency
- 전체 image/state/action 로그

rollout 데이터가 없다면 프로토콜과 실행 준비 상태만 작성하고 성공률 표에 임의의 값을 넣지 마라.

# 17. 구현 및 검증 원칙

- 기존 코드와 결과를 먼저 확인한 후 구현한다.
- 중복 코드를 최소화한다.
- 공통 metric, plotting, loader는 모듈화한다.
- 모든 실행 명령을 README에 기록한다.
- random seed와 config를 저장한다.
- 작은 subset으로 smoke test 후 전체 데이터를 실행한다.
- 결과 파일이 존재한다는 이유만으로 성공으로 판단하지 말고 내용과 sample count를 확인한다.
- figure의 축, 단위, 범례, sample 수를 명확히 표시한다.
- frame 수와 episode 수를 혼동하지 않는다.
- 데이터가 부족하면 분석을 중단하지 말고 가능한 부분까지 수행한 후 정확한 부족 항목을 보고한다.
- 테스트 데이터 누수를 검사한다.
- correction direction이나 threshold를 전체 데이터에서 선택하지 않는다.
- 기존 파일을 삭제하거나 덮어쓰지 않는다.
- 실제 로봇 명령을 자동으로 실행하지 않는다.
- closed-loop 제어는 코드 준비와 안전 검증까지만 수행하고, 실제 로봇 실행은 사용자의 명시적인 지시가 있을 때만 진행한다.

3. 새 데이터 구조와 로그 확인
4. 데이터 무결성 검사
5. preprocessing 검증
6. trajectory/frame 정렬
7. phase 분할
8. observation gap 분석
9. representation gap 분석
10. Shadow Mode 로그 존재 여부 확인
