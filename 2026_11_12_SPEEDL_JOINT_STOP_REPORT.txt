3. 실제 실행 로그 범위와 필요한 coverage

실물 arm 명령이 기록된 trial 18개에서 유효 JointState 173115행을 집계했다.
joint name으로 정렬했으며 degree 변환 시 ±180도로 wrapping하지 않았다.
이 행 수는 독립 시도 수가 아니며, 시작 전/운동 중/정지 후 표본을 포함한다.

4. 제한값 출처 구분

(a) 코드/URDF 모델 제한
validation/a0509_project/urdf/a0509.urdf 및 두산 description xacro는 대략
J1/J2/J4/J5/J6 ±360도, J3 ±160도이다. URDF 소수점 반올림 차이가 있다.
이는 controller 현재 활성 안전 제한의 증거가 아니다.

(b) 매뉴얼 기본 안전 제한과 이번 오프라인 검사 기준
J1 ±360, J2 ±95, J3 ±135, J4 ±360, J5 ±135, J6 ±360도.
configs/joint_safety.yaml에 보수적 envelope로 명시했고 controller_limits_verified=false.
다른 기존 설정을 바꾸거나 URDF 제한을 확대하지 않았다.

(c) controller 역사적 확인값
11:14와 12:53 실행의 alarm 9008은 J5 minimum=-135도를 명시했다.
현재 세션의 J1~J6 활성 하한/상한 전체는 UNKNOWN이다. 이전 alarm을 현재 controller
전체 설정으로 승격하지 않았다. controller 읽기/쓰기는 이번 작업에서 하지 않았다.

정확한 현재 설정과 비교한 '필수 확대량'은 아직 확정할 수 없다. required_ranges.json과
range_comparison.csv는 위 기본 envelope 대비 수학적 coverage와 비교 출처를 저장한다.
실제 안전 제한 변경 검토는 현재 controller 값, 원본 학습 데이터, 실제 툴/배선/
작업영역의 적용 조건이 별도로 확보된 뒤 구분해서 진행해야 한다.

5. 구현한 SpeedL 관절 보호

speedl_experimental/joint_safety.py:
- A0509 URDF의 geometric Jacobian을 계산한다. 선속도 mm/s는 m/s로, 각속도
  deg/s는 rad/s로 변환하고 BASE twist를 관절 속도로 푼다.
- 현재 관절값 이름·유효성·freshness, source/receive gap을 검사한다.
- 0.2초와 관절 수신 age를 합친 구간을 기본 0.02초 단위로 적분해 관절 min/max를
  예측한다. 수치적 특이점, 과대한 관절 속도, 관절 범위 초과면 차단한다.
- 요청 target pose가 있으면 현재 관절을 seed로 한 local IK 경로와 도착값도 검사한다.
- 각도 wrapping으로 J1/J5 초과를 감추지 않는다.
- ProtectedSpeedLBoundary는 검사 결과를 로깅하고, 직전 age/범위를 다시 검사한 뒤
  전달한다. logger 오류·지연, stale source, 범위 초과 후에는 latch inhibit한다.
- 비정상 속도/가속도 배열, NaN/Inf, 과도한 command time, 기존 task 속도/가속도
  초과도 거부한다. 오류 이후 자동 복구/재개/재시도는 없다.
- constructor는 실제 transport를 생성하지 않는다. 테스트에서는 list에 저장하는
  fake callback만 사용했다.

speedl_experimental/controller.py:
- protected_candidate()를 추가해 SpeedL 속도 계산과 관절 예측 결과를 연결했다.
- 관절 검사에서 거부하면 shadow controller를 inhibit하고 원인을 반환한다.
- shadow candidate는 실제 dispatch 승인이 아니다. 물리 호출부가 생기더라도 반드시
  ProtectedSpeedLBoundary와 기존 runtime/sensor/logger gate를 거쳐야 한다.

중요한 검증 한계:
이 예측은 nominal URDF 기반 local differential/IK estimate다. controller의 실제
IK branch, 충돌, 정확한 TCP offset, 제동거리/지연, 시간 정렬을 보증하지 않는다.
controller_limits_verified, physical_speedl_contract_verified,
stop_latency_bound_verified 중 하나라도 미확인이면 실제 dispatch를 허용하지 않는다.
현재 모두 미확인이며 원래 안전 제한을 우회하지 않는다.

6. 기록 기반 SpeedL 비구동 계산

110547, 111406, 125319 세 trial의 409개 prediction/기록 target을 계산했다.
이는 독립적인 첫 tick 후보 평가이며, 제어기를 바꾼 이후의 실제 전체 closed-loop
trajectory를 재현한 시뮬레이션이 아니다. 앞선 두 로그는 pose source timestamp가
없어 기록된 policy decision 시각을 정렬 기준으로 사용했다. 후속 로그도 서비스
응답 시각만 있으며 controller 내부 측정 시각이 검증된 것은 아니다.

nominal 기하 검사 통과: 381
관절 제한 거부: 28
  이미 실측 J5가 범위 밖: 18
  seeded target IK 경로에서 초과 예상: 9
  속도 적분 lookahead에서 초과 예상: 1
실제 물리 dispatch 허용: 0

즉 28개 모두를 사전 예측 성공이라고 부르지 않는다. 18개는 이미 벗어난 상태의
추가 명령 차단이다. 나머지 10개만 해당 계산에서 아직 범위 안의 관절값으로부터
추가 초과를 예상한 사례다. 381개도 전체 physical rollout 안전성 PASS가 아니다.

7. Stop ACK 실패 분석 및 코드 변경

저장 로그에서 111406/125319는 J5 alarm 9008과 state10/SAFE_OFF2 후 HOLD(3)를
요청했고 success=false였다. alarm timestamp 추정값에서 stop 요청까지는 각각
약 55ms / 144ms이다. 관절 측정값이 -135도를 처음 지난 시점부터 stop 요청까지는
이전 audit에서 약 3.54초 / 3.62초로 기록했다.

이것은 한계 진입 후 상태 변화와 stop 실패의 시간적 연계를 지지한다. 하지만
이미 SAFE_OFF2라 요청이 거절된 것인지, SDK return/state/authority 조건 때문인지,
별도 stop 경로 결함인지는 기존 로그만으로 확정할 수 없다. 강제 reset/retry를
추가하지 않았다. stop 실패를 '가속도 문제로 해결됨'이라고 기록하지 않는다.

servo_experimental/stop_evidence.py 및 기존 StreamGuard/ServoL 종료부 변경:
- Stop ACK success=true 하나만으로 정지 성공을 판단하지 않는다.
- 정지 요청 이후의 fresh STANDBY 응답과 연속 0.2초의 실제 관절 velocity 정확한
  0 window를 요구한다. 기존 settle criterion을 재사용한다.
- source/receive gap·회귀, stale/과거 상태, 관절 이동 지속, 증거 누락은 실패다.
- stop 확인 실패/UNKNOWN이면 runtime INVALID이며 future publish는 영구 차단된다.
- stop 성공도 같은 trial을 다시 열지 않는다. double abort는 stop 요청을 중복시키지
  않는다. 첫 원인과 stop 확인 실패 근거를 구분해 남긴다.
- 기존 ServoL launcher는 이 정지 확인 강화만 연결했다. 새로운 SpeedL 물리 publisher나
  실행 launcher는 추가하지 않았으며 기존 ServoL 명령을 SpeedL로 몰래 전환하지 않았다.
